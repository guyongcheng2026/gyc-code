## 一、总体立场
**pi 与 Claude Code 的差距，本质是「设计取向」差异，不是「能力缺失」。**

- **Claude Code** = 内置电池的操作系统（40+ 工具、100+ 命令、sub-agent、plan mode、KAIROS 自主进化全塞进内核）
- **pi** = 极简内核 + 强扩展（只给 read/write/edit/bash 4 工具 + 完整事件系统 + TypeScript Extensions + Agent Skills 标准），官方明确写「skips features like sub agents and plan mode… install a third party pi package」

**结论**：pi 缺失的几乎所有能力，都能通过「Extension（TS 模块）/ Skill / AGENTS.md」注入补齐，无需改内核（与 Codex 复刻 Claude 的路线完全一致）。真正的结构性短板集中在 4 处：多 Agent 编排、Plan 模式、原生 LSP、自主进化（自动记忆/梦境/主动循环）。

## 八、pi 扩展加载修复（2026-08-22 追加）

**问题**：`pi` 启动时 4 个扩展加载失败（2 个报 `pi is not defined`，2 个报 `ParseError: C:\: Unexpected token`），无法正常对话。

**根因**：
1. 扩展 API 注入方式错误：pi 只调用模块「默认导出函数」并传入 API 对象，无全局 `pi`。`gyc-orchestrator` 在模块顶层用 `pi.events.on(...)`、`lsp` 全部命令在顶层用 `pi.registerCommand(...)` → `pi is not defined`。
2. 语法错误：`lsp/index.ts` 的 `lsp-diagnostics` 处理器缺右花括号；`C:\temp\pi-extensions\gyc-orchestrator` 的 `runSubagent` 少了 `);`、`decomposeTask` 多一个 `}`。
3. `lsp`（C:\temp 副本）缺 `import { Type } from "typebox"`。
4. 生命周期事件 API 用错：`pi.events` 是扩展间消息总线，事件订阅应为 `pi.on("agent_end", ...)`。

**修复文件（4 个）**：
- `C:\Users\谷勇成\.pi\agent\extensions\gyc-orchestrator\index.ts`
- `C:\Users\谷勇成\.pi\agent\extensions\lsp\index.ts`
- `C:\temp\pi-extensions\gyc-orchestrator\index.ts`
- `C:\temp\pi-extensions\lsp\index.ts`

**验证**：`pi --help` 无扩展报错；`pi -p "回复：OK"` 正常返回 `OK`。

**遗留建议**：`.pi\agent\extensions` 与 `settings.json` packages（C:\temp\pi-extensions）存在双份同源扩展，会重复注册命令，建议后续二选一去重。
