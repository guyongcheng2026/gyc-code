## 一、现象

- TUI / Compose 会话运行 DeepSeek V4 Flash 时报错：
  `LLM stream connection idle timeout: no data received within 300000ms. The connection may have dropped.`
- 会话中断，gyc cli 无法继续正常运行

## 二、排查结论

- 根因 1：`llm-timeout.ts` 流空闲超时默认 300s（5 分钟），DeepSeek V4 Flash（opencode 免费通道 / 代理排队）首 token 延迟或连接 hang 可超过该窗口
- 根因 2：超时错误消息 `connection idle timeout / no data received` 不匹配 `retry.ts` 的 `RETRYABLE_MESSAGE_PATTERNS`，被判为不可重试 → 直接失败终止，而非自动重试恢复

## 三、修复（commit `da08605`）

1. `src/gyccode/session/retry.ts`：`RETRYABLE_MESSAGE_PATTERNS` 增加 `idle` 关键词与 `/\bidle timeout\b|no data received/i`，空闲超时错误进入自动重试（最多 5 次，指数退避 2s→30s）
2. `src/gyccode/session/llm-timeout.ts`：默认 `LLM_STREAM_IDLE_TIMEOUT_MS` 300s → 600s（10 分钟），适配 DeepSeek V4 慢首 token
3. `src/core/v1/config/config.ts`：schema 描述默认值同步 600000
4. 新增 `retry.test.ts`（idle timeout 可重试 / 普通错误不可重试）；更新 `llm-timeout.test.ts` 断言
5. 用户配置 `~/.config/gyccode/gyccode.json` 增加 `llm.stream_idle_timeout_ms: 600000`（立即生效，无需等发布）

## 九、稳定性修复：LLM provider 超时导致 runLoop 静默阻塞数分钟（2026-08-12 晚间）
> commit `e3546d8`；现象：LLM 运行几分钟后失去响应，需要重发消息才能恢复

### 现象与证据
- 日志（`~/.local/share/gyccode/log/gyccode.log`）：provider（nvidia/nemotron）反复 `ProviderHeaderTimeoutError: Provider response headers timed out after 60000ms`，每次重试等 60s 后再发起，循环 5+ 次，runLoop 静默阻塞数分钟，期间 TUI 无响应

### 根因链路
- `processor.ts`：`llm.stream` 的 `Stream.runDrain` 阻塞；外层 `Effect.retry` 最多 5 次
- `retry.ts`：`HeaderTimeoutError` 被标记 `isRetryable`；重试单次最长 60s、无总时长上限，60s×5 约 6 分钟静默
- 并发闸（`Semaphore` 6）已确认正常，非并发问题

### 修复（commit `e3546d8`）
1. `retry.ts`：新增 `RETRY_TOTAL_CAP_MS = 120_000`，重试累计耗时超 2 分钟立即放弃并报错，不再静默空等
2. `llm-timeout.ts`：新增 `LLM_FIRST_TOKEN_TIMEOUT_MS = 180_000` + `resolveFirstTokenTimeout` + `withFirstEventTimeout`（`Stream.toPull` + `Effect.timeout` 首帧快速失败，成功后重放首帧续拉）
3. `llm.ts`：AI SDK 转换流外层包 `withFirstEventTimeout`，再套 `streamWithIdleTimeout`（idle 超时仍负责流中段停滞）
4. 配置：`llm.first_token_timeout_ms` 可调（默认 180000，配置项提交 `463fd17`）
