## 十一、DeepSeek 官方通道缓存命中优化与实测（2026-08-11）

### 背景
- 目标：deepseek-v4-flash（官方 API，high）缓存命中率 ≥98.2%
- 现状基线：本地库 5 个 flash-free 会话加权命中率约 88%（86.1%~96.6%），官方 API 历史会话 90.9%~92.7%（均混用多模型，非纯净数据）

### P0 四项落地（gyc-cli commit d8c8444）
1. **日期移出缓存前缀**：`Today's date` 完全移出 system（实测发现 DeepSeek 对 system 消息要求字节完全一致，任何位置变化都整段失效），改为注入最新 user 消息文本前缀（`prompt.ts`）→ 跨天只影响当轮增量，历史前缀完整保留
2. **记忆注入会话级固定**：`sys.memory(query, sessionID)` 增加按 sessionID 的 30 分钟 TTL 缓存 → 同一会话内记忆段字节级稳定
3. **微压缩调优**：`MICROCOMPACT_THRESHOLD 0.85→0.9`、`CACHE_PREFIX_KEEP 10→20`（compaction.ts + microcompact-select.ts + 测试同步）
4. **单模型锁定**（使用约束）：会话全程固定 `deepseek/deepseek-v4-flash --variant high`，禁止中途切换模型

### 实测结论（scripts/cache-probe.mjs + cache-compare.mjs，官方 API 真实调用）
- 40 轮 / 165.9 万 token / effort=high：综合命中率 **94.98%**，末轮单轮 **97.36%**
- 规律：官方 API 缓存「每轮仅新增部分未命中，上一轮全部命中」→ **综合命中率 ≈ 1 − 2/N**（N=轮数）
- 达到 >98.2% 需要会话 ≥110 轮（约 1300 万 token），与增量大小无关；短会话（<60 轮）统计上不可能达标
- 128-token 块对齐损耗仅在每轮增量小时显著；真实 agent 会话增量（K 级）无影响

### 改进效果对照实测（cache-compare.mjs，跨天+记忆变化场景）
- 布局 A（改进前：日期在 env 中段 + 记忆随轮变化）：**全部轮次命中率 0%**（system 每轮变化 → DeepSeek 整段不缓存）
- 布局 B（日期在 system 尾部 + 记忆固定）：同日轮正常（35%→92.7%），但**跨天轮 0%** → 证明日期必须在 system 之外
- 布局 C（最终方案：system 完全静态 + 日期注入最新 user 消息）：同日轮 35%→92.5%，**跨天轮 92.9%**（与同日持平，前缀不受跨天影响）
- 结论：P0 四项中「日期移出 system + 记忆会话级固定 + 微压缩调优 + 单模型锁定」组合后，官方 API 长会话可稳定逼近 98.2%（≥110 轮）

### 第二轮实测：120 轮小增量验证（2026-08-11 深夜，官方 API）
- 实验：`bun scripts/cache-probe.mjs 120 deepseek-v4-flash high 15`（每轮工具输出 15 行 ≈570 token，含消息开销每轮增量 ≈843 token）
- **结果：综合命中率 98.31%（>98.2% 达标）**，累计命中 600.5 万 / 未命中 10.3 万 / 总输入 610.8 万 token，末轮单轮 99.23%
- 120 轮时 prompt 101,130 token（128K 上下文内），与理论值 1-2/120=98.33% 完全吻合 -> 公式「综合命中率 ≈ 1-2/N」成立
- 结论：命中率只取决于「压缩前能跑多少轮 N」：98.2% ⇔ N≥112 ⇔ 每轮增量 ≤ 0.9×128K/112 ≈ 1.03K token

### 根因分析与护栏落地（gyc-cli commit 943527c）
- 根因：truncate.ts 允许单条工具输出落盘 50KB（≈12.5K token），注入层 aggregateToolCaps 单条 assistant 消息预算 100K 字符 -> 一轮可注入数十 K token -> 128K 只够几轮就触发微压缩 -> 前缀破坏 -> 命中率暴跌
- 落地「缓存增量预算」护栏：
  - message-v2.ts 新增 cacheFriendlyBudget(contextLimit)：上下文窗口 ≤200K 的模型（DeepSeek 128K）单条工具输出注入 ≤1.5K 字符（≈400 token）、单条 assistant 消息合计 ≤24K 字符；大窗口模型不收紧
  - 冻结截断决策（callID 记忆）保持历史前缀字节稳定，只对新增消息生效，不破坏缓存
  - prompt.ts 主请求路径按 model.limit.context 传入预算
- 验证：message-v2.cache.test.ts 新增 3 项测试（maxPerChar 生效/冻结稳定/窗口判定），24 项全过；bun run build.mjs 通过

### 结论（可落地性）
- 对话型长会话（每轮 1-2 个工具调用、输出适中）：每轮增量 ≈0.6-1K token -> 128K 内可跑 115-190 轮 -> 综合命中率 98.3-98.9% ✓
