## 一、故障现象

`gyc` 命令无法启动：

```
PS C:\Users\谷勇成> gyc
error: No such built-in module: node:sqlite
Bun v1.3.14 (Windows x64)
```

## 二、根因分析

1. **项目方向**：`build.mjs` 默认 `GYC_RUNTIME=node`，打包条件 `["node","browser"]` → `#sqlite` 解析到 `sqlite.node.ts` → dist 产物为 **Node 目标**（含 `import { DatabaseSync } from "node:sqlite"`，需 Node ≥ 22.5）。
2. **入口矛盾**：`bin/gyc` 在 Bun 环境（`typeof Bun !== "undefined"`）下优先 `import(dist/index.js)`，加载的却是 Node 目标产物；Bun 1.3.14 不支持 `node:sqlite` → 崩溃。
3. **触发面**：谷总本机 `gyc.exe` 安装在 `.bun/bin`（Bun 全局链接），必然走 Bun 分支。

## 三、修复方案（commit `84e2360`）

采用**构建运行时标记**方案（O(1) 判断、零误判，避免启动时全扫 285 个 chunk）：

1. `build.mjs`：构建完成后写入 `dist/RUNTIME` 标记（内容 `node` / `bun`）。
2. `bin/gyc`：
   - Bun 分支：标记为 `bun` → 进程内 `import`（冷启动最快）；否则（`node` 或无标记，默认 node）→ 交给 Node 子进程直跑 dist。
   - Node 分支：标记为 `bun` → spawn Bun 跑（防御性）；否则直接 `import` dist。
   - 新增 `findNode()` / `findBun()`，支持 `GYC_NODE` / `GYC_BUN` 环境变量覆盖。

## 六、TUI 双运行时修复（commit `4e66723`）

> 关联：[[2001.我的助手工具链/gyc-code-项目架构|gyc-code 项目架构]]

### 1. 故障现象

`gyc` 报 `Error: Unexpected error` / `Worker is not defined`（Node 25 无全局 Web Worker），逐层暴露新错误：

1. `Worker is not defined` — tui.ts 用 Web Worker 全局，Node 25 无
2. `@opentui/solid/runtime-plugin-support` Bun-only — Node 顶层 import 抛错（依赖 Bun 插件系统）
3. `OpenTUI native FFI is not available for this runtime yet` — @opentui/core Node 后端 require `node:ffi`，**实测 Node v25.9 / Bun 1.3 均无此模块**

**核心矛盾**：主进程已迁 Node（内存/启动优势），但 OpenTUI 原生渲染仅支持 Bun（`bun:ffi`），Node 侧 `node:ffi` 模块根本不存在。

### 2. 修复方案：双运行时策略

| 命令类型 | 运行时 | 产物 |
|---------|--------|------|
| 非 TUI 命令（run/agent/serve/--help/--version 等） | Node 直跑 | `dist/`（node 目标） |
| TUI 命令（默认 `gyc`、`gyc --mini`、带 project 参数） | Bun 子进程 | `dist-bun/`（bun 目标） |

1. **build.mjs**：双目标构建。node → `dist/`，bun → `dist-bun/`（bun 目标附加 `"bun"` 条件，@opentui/* 解析 bun 版产物，与 dev 命令一致）。
2. **index.ts**：Node 主进程检测默认 TUI 命令（`!process.versions.bun`）→ `spawnTuiUnderBun()`：spawn Bun 跑 `dist-bun/index.js`，参数/退出码透传；非 TUI 命令不受影响。
3. **tui.ts**：worker 线程恢复 Web Worker API（Bun 下原生支持，`new Worker(file)`）。
4. **rpc.ts**：`channel()` 消息通道统一适配（Web Worker 全局优先，node:worker_threads parentPort 兜底）。
5. **runtime.ts**：runtime-plugin-support 改动态 import + 容错降级（Bun 正常注册，Node 静默跳过）。
6. **.gitignore**：忽略 `dist-bun/`。

## 第六节：默认入口改造为纯 CLI（gyc 无参 readline 对话 / gyc tui 显式子命令）

**目标**：`gyc` 默认入口从全屏 TUI 改为纯 CLI——无参进入逐行对话（Node 直跑，无 OpenTUI 依赖），传消息/管道走非交互单轮（等价 `gyc run`），`gyc tui` 成为显式全屏 TUI 子命令。

### 1. 实施内容

- **新增 `src/gyccode/cli/cmd/default.ts`**（DefaultCommand，`$0 [message..]`）三形态分发：
  1. 传消息或 stdin 管道 → 非交互单轮，**复用 `RunCommand.handler`**（行为与 `gyc run` 完全一致）
  2. 无参数且 stdout 为 TTY → `node:readline/promises` 逐行对话（`gyc>` 提示符，`/exit` `/quit` `/help` `/<command>` 斜杠命令，Ctrl-C 退出）
  3. `--mini` → 转发 `runMini`（split-footer 交互，需 Bun）
- **新增 `src/gyccode/cli/cmd/run/stream-cli.ts`**：从 run.ts 提取流式渲染逻辑（loop/emit/tool/toolError/inline/block），run 与 default 共用，保证两入口输出一致
- **`tui.ts`**：命令名 `$0 [project]` → `tui [project]`，成为显式子命令
- **`index.ts`**：COMMANDS 注册 `tui`；默认分支挂 DefaultCommand；Node 下 `gyc tui` / `gyc --mini` 提升到 Bun 子进程（spawnTuiUnderBun）
- **`read-stdin.ts`**：`readableEnded` 防护——stdin EOF 后二次读取直接返回空串，避免永久挂起（转发场景 stdin 已被消费）

### 2. 关键问题与修复

| 问题 | 根因 | 修复 |
|------|------|------|
| 转发后无输出挂起 | default.ts 先 readStdin 消费 stdin，run.ts handler 内二次 readStdin 等 EOF 永不返回（Node end 事件不重复触发） | read-stdin.ts 加 readableEnded 防护；default.ts 仅在无 message/command 时才读 stdin |
| 覆盖 run/stream.ts | 原文件已存在（mini 模式 footer 桥接），被同名新文件覆盖 | git 恢复原文件，新模块改名 stream-cli.ts |
| 参数模式挂起 | 有 message 时仍 await readStdin（stdin 继承未关闭） | default.ts 有 message/command 时不读 stdin |

## 第七节：CLI 交互内模式切换（4e49bd6）

### 1. 背景

谷总演示：`gyc` 交互模式里输入 `gyc tui` / `gyc --mini` 被当成普通消息发给 LLM（浪费一次调用 + 429 报错）。要求三种入口（`gyc` / `gyc tui` / `gyc --mini`）都能正常使用。

### 2. 方案

- **识别模式切换**：交互循环里正则识别 `gyc tui` / `tui` / `gyc --mini` / `--mini` / `-i`，不再当普通消息；其他 `gyc <子命令>` 输入提示「交互模式内仅支持 tui / --mini 切换」。
- **切换即退出**：先 `rl.close()` 恢复终端，再 `spawnSync` Bun 子进程跑 dist-bun 接管全屏交互；子进程退出后本 CLI 进程 `process.exit(code)`。切换后回 shell，会话各自独立（子进程是新 server 实例，无法延续 CLI 进程内存中的会话）。
- **公共模块**：新增 `src/gyccode/cli/util/bun-runtime.ts`（`resolveBunRuntime` + `spawnBunSync`），从 import.meta.url 逐级向上找 dist-bun，兼容打包后 chunk 布局；index.ts 的 `spawnTuiUnderBun` 改用它去重。

### 3. 排查过程（关键坑）

| 尝试 | 结果 |
|------|------|
| 切换传 `--session` 续会话 | ❌ `Session not found`：spawn 的 TUI 是新 server 实例，找不到 CLI 进程内存中的会话 |
| 不传 session，spawnSync 后回到 CLI 循环 | ❌ **mini 退出后**再切 TUI 稳定挂起（TUI 只输出 keymap 警告不渲染）；但 pty 直接跑 `gyc tui` 正常、CLI 里直接 `gyc tui`（无 mini 前置）也正常 |
| `rl.close()` 恢复终端后再 spawnSync，切换后退出 CLI | ✅ 全场景通过 |

根因推测：mini（OpenTUI）在 CLI 进程内运行/销毁后，readline 的终端模式与 console input 状态残留，spawnSync 继承后导致 TUI 初始化挂起。关闭 readline 恢复终端后问题消失。
