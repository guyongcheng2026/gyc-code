1. **截断事故**：低内存机器编辑大文件，结尾易被意外截断，且"语法不完整"的截断 lint 不报、只有 `bun build` 能发现（Expected { but found end of file）。每次改动后必须 bun build 全依赖图冒烟验证，不能只信 lint。
2. **SSE 泄漏机理**：hey-api `createSseClient` 的 finally 仅 releaseLock 不 cancel，只有 `subscribe({ signal })` 且轮次结束 abort 才会 `reader.cancel()` 真正关闭连接；凡每轮新建订阅的调用点都必须配 AbortController + try/finally abort，进程级一次性调用除外。

4. **测试 mock 去 any 模式**：用 `Parameters<typeof fn>` / `ReturnType<Halt>` 等从被测函数签名反推精确类型，可把 mock 的 `: any` / `as any` 干净归零且运行时零变化。
5. **git 提交乱码复发**：`19ae562` 提交信息再次出现 GBK 双重编码损坏（"限流"类乱码），印证铁律：中文提交信息必须写入 UTF-8 临时文件用 `git commit -F`，禁止命令行直传。
6. **GBK 乱码修复方法论（问题清单修复轮实证）**：
   - 乱码指纹有两类：PUA 区字符（`[\uE000-\uF8FF]`）**和**落在 CJK 常规区的 GBK 误读字（`绠€`/`锛?`/`鈥?`/`浣跨敤`）。**只查 PUA 会漏检一半以上**——正确检测是对每行做 `iconv.encode(line,'gbk')` → UTF-8 解码，结果 ≠ 原文即乱码（`scripts/check-mojibake.mjs` 已固化）。
   - 可逆性分级：无 `?` 替换符的行可 GBK 反向解码无损恢复；含 `?` 的行信息已永久丢失，只能从 git 历史干净版 + 代码上下文语义重建（本轮 terminal.ts 的"干净版本"7f4a6a667c 本身也带 `?`，说明损坏分多轮累积）。

### NUL 类保留名处理经验（补充事故复盘）

- `statSync("NUL")`（相对路径）会解析到 **DOS 设备**而非磁盘真实文件，`isDirectory()` 结果不可信——判定必须用 `\\?\` 绝对前缀路径。
- 删除保留名文件的安全原语是 `unlinkSync("\\\\?\\<abs>")`（单目标、非递归、绕过 DOS 设备解析）；`readdirSync`/scandir 对这类路径报 EISDIR 不可用；**严禁 `rd /s /q \\?\...`**（递归展开正是整仓误删事故的机制）。
