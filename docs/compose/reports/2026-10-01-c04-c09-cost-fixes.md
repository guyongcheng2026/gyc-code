## 二、`gyc stats` 3.9% 口径差额：根因

### 实测数据

对偏差会话 `ses_f2f26a44cffePdmSm4HWrAYtg6` 三口径对照：

```
session.cost           = 7.641453
step-finish part 合计  = 6.904922   (1340 条)
assistant message 合计 = 6.904922   (1354 条)
差额                   = 0.736532
```

### 结论

**part 合计与 message 合计完全相等**（6.904922 = 6.904922）。C-06 关心的两条逐轮路径本来就一致；真正偏离的是 `session.cost` 这个**运行计数器**。

`session.cost` 历史上把**已被删除的 part 的成本也累加在内，而 `sign=-1` 回退未能完全抵消** —— 这正是 C-05 报告描述的原始病灶：

> 消息改写 / 重投影时旧成本被扣回、新成本被加上 …… 成本会被追溯调整，「今天花了多少」不是一个稳定值。

### 处置

- append-only 改动从结构上消除了这类追溯改写，**新数据不会再产生该偏差**
- **历史数据已损坏且不会自愈**（当时无流水可依据）
- 建议：一次回填迁移，按 step-finish part 重算历史 `session.cost`。会改动历史统计值，需另行确认后再实施

### 排查过程中被证伪的两个假设（留档避免重复劳动）

1. **「`rollupUsage` 从未执行 / step-finish part 为 0 条」** —— 错误。用 drizzle 表对象查 `json_extract` + 分组时静默返回空，换裸 SQL 才得到真实的 1340 条。**教训：诊断投影表里的 JSON 列时用裸 SQL，不要信 drizzle 的封装结果。**
2. **「差额来自子代理成本上卷」** —— 错误。子会话合计 0.798 与偏差 0.737 数值接近属巧合；且子代理上卷无法解释 part 合计已与 message 合计相等这一事实。**教训：数值接近不等于因果。**
