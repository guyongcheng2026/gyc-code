# 架构审查 ROUND3：六问题深挖与对标 Claude Code 落地方案
> 日期：2026-08-12
> 范围：发热/噪音/幻觉率/缓存命中率/CLI 启动包/存储数据库六类问题根因重审 + 对标 Claude Code + 本机硬件（Intel Core i5-5250U，2015 超低电压双核四线程，15W TDP，睿频 2.7GHz）约束下的最佳方案
> 结论先行：本次落地 4 项治本改动（中间态事件不落库 / 幻觉防护全提示词覆盖 / bun 直跑冷启动 / ERROR 日志限流），DB 182.3→136MB，冷启动 2.90→1.26s，全量 375 测试 0 失败。

## 一、六类问题根因与对标结论

### [1] 发热/风扇噪音（CPU 高占用）
- **实测**：空闲 CPU 已低（~1% 单核）；发热主因是「流式渲染峰值 + 内存换页」，前轮已通过 30ms 节流、降级渲染（默认关语法高亮）、Delta 事件节流治理。
- **仍存在的隐性 CPU 消耗**：
  - v1 路径每个 tool 的 pending/running 状态变更都触发一次「event 持久化 + 投影 part 表」的同步 DB 写（SQLite 写放大 + fsync）。
  - 失败重试期间同 run 重复 ERROR 全量落盘（日志 IO）。
- **对标 Claude Code**：CC 流式中间态只在内存，最终消息才持久化；失败重试带退避且日志分级。
- **最佳方案（已实施）**：① 中间态改 publishLive + 直投影 part 表（零 durable 写）；② ERROR 日志 60s 同类限流。
- **本机约束**：i5-5250U 对 IO 峰值敏感，减少每 token/每工具一次 DB 写即直接降发热。

### [2] 噪音
- **根因 A（日志刷屏）**：provider 60s 超时/限流时，同 run 每步重试 3 次，每次写一条完整 ERROR（含 stack），日志 12.8MB。
- **根因 B（历史）**：read/write 误拒、内存泄漏告警等已修复。
- **对标 Claude Code**：ERROR 聚合（同源错误合并计数），INFO 默认不落盘。
- **最佳方案（已实施）**：fileLogger 对同 run+同 message 的 ERROR 做 60s 限流，日志量骤降且不丢错误状态。
- **待办**：GYCCODE_LOG_LEVEL 默认 INFO 已有；可考虑启动时对 log/gyccode.log.1 自动轮转删除。

### [3] 幻觉率高
- **根因**：系统提示词 15 份中仅 beast/trinity/gpt/copilot-gpt-5 有防幻觉段落；**default.txt（当前主力 deepseek 走 default）等 6 份完全缺失**。记忆 freshness 提醒、websearch 引用提示已有。
- **对标 Claude Code**：所有模型统一「不确定即声明 + 证据引用（file:line/命令输出）+ 区分已验证与推断」。
- **最佳方案（已实施）**：统一防幻觉段落补全至 default/anthropic/gemini/kimi/meta/codex 共 10 份；段落固定位置、字节稳定（prompt cache 友好）。
- **补充建议**：① 小模型（summary/title/记忆提取）不参与主对话推理（已配 small_model）；② 工具结果引用强制要求（已有 websearch 引用提示，可推广到 read/grep）。

### [4] 缓存命中率待提高
- **根因（已闭环确认）**：当前模型 opencode/deepseek-v4-flash-free 不报告 prompt caching，命中率 0% 是模型能力限制，非代码缺陷。
- **已具备**：promptCacheKey 覆盖 openai/azure/xai/mistral/openai-compatible/venice/gateway；系统提示字节稳定（记忆 30min 缓存、environment 固定、tool cap 冻结、truncation 决策冻结）。
- **对标 Claude Code**：CC 对支持缓存的模型（Claude/GPT）用 cache_control 断点 + promptCacheKey。
- **最佳方案**：换支持缓存的模型后跑 `gyc db cache` 验证；提示词防幻觉段落已按「前缀稳定」插入，不破坏缓存。
- **待办**：anthropic 协议的 cache_control 断点策略（src/llm/protocols/anthropic-messages.ts 已有 4 断点上限），切 Claude 模型时按需启用。

### [5] CLI 启动包较大
- **实测**：dist 232.6MB / 4645 chunks；冷启动 `gyc --version` 2.90s（node 包装层 0.33s + bun 启动 0.58s + 模块加载 0.75s + 进程创建开销）。
- **根因**：bin/gyc 用 node spawnSync bun = 双进程三层链（bun shim → node → bun）。
- **对标 Claude Code**：冷启动 <2s，bun compile 单文件分发。
- **最佳方案（已实施）**：bin/gyc 改 bun shebang 直跑，bun 下同进程 import dist/index.js；实测 `gyc --version` 2.90s→1.26s（热 0.86s），达标且低于 CC 阈值。
- **待办（可选）**：bun build --compile 单 exe 分发（启动更快，但产物 ~250MB+ 且 npm 分发链路需重设计）；依赖剪枝（@ai-sdk 全家桶按需保留）可将 dist 压到 ~150MB。

### [6] 存储及数据库文件较大
- **实测**：DB 182.3MB + WAL 4MB；event 表 message.part.updated 39821 行 / 98.5MB，其中 **tool 类 25981 行 / 91.1MB**。
- **根因（治本）**：v1 路径（TUI 实际使用）每个 tool 经历 pending→running→completed 三次 updatePart，每次都把完整 part 快照（含大 output）写入 event 表 + 投影 part 表；text/reasoning 各 start+end 两次。
- **对标 Claude Code**：只持久化最终消息，流式中间态在内存。
- **最佳方案（已实施）**：新增 Session.updatePartLive —— 中间态 publishLive（TUI 实时可见）+ 直投影 part 表（运行中读取一致），**不写 event 表**；仅最终态（completed/error/text-end/finishReasoning）走 durable。
- **已实施清理**：maintain-data --prune-events=8 --clean --checkpoint + VACUUM：DB 182.3→136.0MB（回收 46MB），event 表 part.updated 39821→27074 行。
- **未来增量**：每 part 仅 1 条最终态 event，不再随 token/工具状态膨胀。
- **待办（用户决策）**：历史超大会话（如 ses_00e957… 6.6MB）可按需 prune-events=4 进一步压缩；tool-output 36.5MB 保留期 7 天可缩短。
