## 二、与 opentui 的定性对比

| 维度 | opentui（现状） | fallback（PoC） |
|------|----------------|-----------------|
| 依赖 | 原生 Zig DLL + FFI + koffi 补丁链 | 纯 JS/TS，零原生依赖 |
| 失效模式 | DLL 加载失败/原生崩溃即全挂，无降级路径 | V8 堆内运行，异常可捕获可降级 |
| 宽度口径 | unicode/wcwidth 双模式需 env 强制对齐 | string-width 单一口径，与 display-width 同源 |
| 组件生态 | SolidJS reconciler + 完整组件树 | 仅命令式网格 API，无组件层 |
| 内存可观测性 | Zig arena 分配 JS 层不可见 | 全在 V8 堆内，可快照 |

## 三、决策建议

1. **全面替换：暂不立项。** opentui 的 SolidJS 组件树（77 文件 123 处 import）与 tree-sitter 高亮、布局引擎构成深护城河，替换收益不抵迁移风险。
2. **安全模式接入：建议立项（下一阶段）。** 将 fallback 作为 opentui 初始化失败/原生崩溃时的自动降级通道：
   - 新增 `RendererBackend` 抽象与 `GYC_TUI_BACKEND=opentui|fallback|auto` 开关；
   - `auto` 模式在 createCliRenderer 异常时进入 fallback 安全模式（消息流只读 + 单行输入），变「黑屏退出」为「可用保底」；
   - 预估工作量 3–5 天，主要成本在会话消息流的只读适配。
3. **引擎继续孵化价值**：差分帧内核已达标，后续若 opentui 出现不可修复的缺陷，替换路径已打通。

## 四、遗留与风险

- 增量帧的 rowEqual 逐格比较在超大屏（>200 列）下有优化空间（可改行哈希），当前量级无需动；
- input.ts 未覆盖 kitty 键盘协议与修饰键组合，安全模式场景够用；
- Windows 老 conhost 的实际观感需真机人工验收一次。

## 五、结论

PoC 三项硬指标（正确性、性能、字节量）全部达标且余量充足。「自研 fallback 渲染器孵化」路线**技术可行性已证实**，建议按「安全模式接入」立项推进，全面替换维持观望。
