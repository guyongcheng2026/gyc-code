Launch a new actor (subagent) to handle complex, multi-step tasks autonomously.

JSON calls wrap the payload inside an `operation` object; `action` is the discriminator field.
Example: {"operation":{"action":"run","subagent_type":"explore","description":"Find X","prompt":"<full task>"}}

## Operations (the `operation.action` field selects one)

- run:    spawn a subagent and BLOCK until completion; result returned inline.
          required: subagent_type, description, prompt
          optional: actor_id (resume a prior actor), timeout_ms, command, task_id
- spawn:  spawn a subagent and return actor_id IMMEDIATELY (background).
          Requires GYCCODE_EXPERIMENTAL_BACKGROUND_SUBAGENTS=true.
          required: subagent_type, description, prompt
          optional: actor_id, command, task_id
- status: poll actor state without blocking. required: actor_id.
          Returns: { status: "running"|"completed"|"error"|"cancelled"|"unknown", actor_id, ... }
- wait:   block until actor completes (success/failure/cancelled) or timeout (default 10 min).
          required: actor_id. optional: timeout_ms.
          Returns: { status, actor_id, result?, error? }
- cancel: stop a running actor (graceful). required: actor_id. Idempotent.
- send:   NOT supported in gyc-code. Use `run`/`spawn` instead.

## When to use actor

- **Parallelize**: spawn multiple independent searches/analyses concurrently; `wait` on each.
- **Isolate heavy lifting**: delegate 10+ file reads to a subagent; you get only the synthesis.
- **Specialized search**: `explore` for read-only code discovery; `general` for unbiased verification against a spec.
- **Tracked task**: pass `task_id` ONLY if you obtained it this session (never invent one; create the task first or omit it). It is metadata binding only and does not change execution.
- **Don't spawn for**: trivial single-file lookups, answers already in your context, or decisions on partial outputs.

## Writing the prompt

You are the subagent's only briefing — it hasn't seen this conversation.
- Explain what you're trying to accomplish and why; say what you've already learned or ruled out.
- Give enough context for judgment calls, not just narrow steps.
- If you need short output, say so ("report in under 200 words").
- For investigation: hand over the question; prescribed steps become dead weight.

## Usage notes

- **Resume**: pass `actor_id` to `run`/`spawn` to continue that subagent's session (its prior messages and tool outputs). Without it, a fresh subagent is created.
- **`run` vs `spawn`**: `run` blocks and returns the result inline; `spawn` returns actor_id immediately (results arrive as notifications) — use `wait` to block explicitly.
- **Model override**: per-call `model` is accepted for compatibility but ignored — the subagent runs on its agent-configured model.
- Brief subagents well (they don't see your full context). Nested spawning is capped by "subagent_depth" (default 1).

</example>
