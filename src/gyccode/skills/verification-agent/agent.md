# 验证代理 (verification-agent)

## 代理概述
这个技能展示了如何增强pi agent的功能，通过实现专门的验证代理来提供：
1. 以破坏为中心的验证思维（尝试破坏实现而非仅仅确认其有效性）
2. 特定于更改类型的验证策略（前端、后端、CLI、基础设施、库、 bug修复、移动、数据/ML、数据库迁移、重构等）
3. 临时目录隔离用于安全实验
4. 全面的质量门（构建、测试、linters、类型检查器）
5. 与协调者-工作者模式的集成

## 当前限制
pi agent目前的验证能力有限：
- 没有专门的验证代理
- 验证往往是事后的，缺乏系统性
- 没有针对不同更改类型的特定验证策略
- 没有强调寻找缺陷而非仅仅确认功能
- 没有临时目录隔离用于安全实验
- 没有自动化的质量门

## 增强功能

### 1. 以破坏为中心的验证思维
- 专注于寻找方式来破坏实现，而不仅仅是确认其有效性
- 采用“尝试破坏它”的方法来发现隐藏的缺陷
- 识别验证回避模式（读代码、 narrate 什么应该被测试，写“PASS”然后继续）
- 防止被前80%的 polished 外观所迷惑，专注于最后20%的难点

### 2. 特定于更改类型的验证策略
为不同类型的更改提供定制的验证程序：

**前端更改**：
- 启动开发服务器
- 使用浏览器自动化（如果可用）进行导航、截图、点击和控制台读取
- curl 页面子资源（如图片、API路由、静态资源）
- 运行前端测试

**后端/API更改**：
- 启动服务器
- curl/fetch 端点并验证响应形状（不仅仅是状态码）
- 测试错误处理和边缘情况
- 验证响应结构、数据类型和约束

**CLI/脚本更改**：
- 用代表性输入运行
- 验证 stdout/stderr/exit codes
- 测试边缘输入（空、格式错误、边界值）
- 验证 --help / usage 输出的准确性

**基础设施/配置更改**：
- 语法验证
- 干运行（如 terraform plan、kubectl apply --dry-run=server、docker build、nginx -t）
- 检查环境变量和密钥是否实际上被引用而不仅仅是定义

**库/包更改**：
- 构建库
- 运行完整的测试套件
- 从全新上下文中导入库并行使公共API
- 验证导出的类型是否匹配README/文档示例

**Bug修复**：
- 重现原始bug
- 验证修复是否有效
- 运行回归测试
- 检查相关功能的副作用

**移动（iOS/Android）**：
- 清理构建并在模拟器/仿真器上安装
- 转储可访问性/UI树
- 通过标签查找元素，通过树坐标点击
- 截图作为次要验证手段
- 杀死并重新启动以测试持久性
- 检查崩溃日志（logcat / 设备控制台）

**数据/ML管道**：
- 用样本输入运行
- 验证输出的形状/模式/类型
- 测试空输入、单行输入、NaN/null处理
- 检查静默数据丢失（输入行数 vs 输出行数）

**数据库迁移**：
- 执行向上迁移并验证Schema是否符合意图
- 执行向下迁移（可逆性）并在现有数据上测试
- 不仅在空数据库上测试

**重构（无行为变化）**：
- 现有测试套件必须完全未更改地通过
- 公共API表面必须保持不变（没有新增/删除的导出）
- 通过可观察行为相同性进行抽检（相同输入 → 相同输出）

### 3. 临时目录隔离
- 允许在临时目录（/tmp 或 $TMPDIR）中创建测试脚本
- 用于多步骤竞争条件测试或需要文件的实验
- 自动清理临时文件
- 防止对主代码库或环境造成污染

### 4. 全面的质量门
- 自动运行构建系统（如 make、maven、gradle 等）
- 执行项目的测试套件（如 jest、pytest、junit 等）
- 运行配置的linters和类型检查器（如 eslint、tsc、mypy 等）
- 应用格式化工具（如 prettier、black、gofmt 等）
- 这些质量门作为失败的快速通道（例如，损坏的构建即为FAIL）

### 5. 与架构的集成
- 与协调者-工作者模式集成：
  - 可以作为专门的验证工作者创建
  - 协调者可以将验证任务委托给验证代理
  - 验证代理可以报告详细的发现和问题
- 与现有工具集成：
  - 使用所有标准工具（编辑、bash、搜索等）进行验证
  - 可以创建临时任务用于验证操作
  - 结果可以馈送到其他工具或流程中

## 实现方法

这个技能提供了一个如何实现这些增强功能的蓝图。实际的实现需要：
1. 创建验证代理的核心逻辑
2. 实施特定于更改类型的验证策略
3. 添加临时目录隔离和安全实验支持
4. 实施全面的质量门和自动化检查
5. 与协调者-工作者模式和现有工具集成
6. 提供用于配置验证行为和严格程度的选项

然而，这个技能可以通过以下方式使用：
1. 作为参考文档，用于了解应该实现什么
2. 作为教学工具，帮助用户理解验证代理的好处
3. 作为原型，这些增强功能可以在此基础上进行构建

## 使用示例

### 示例1：验证后端API更改
用户请求：“验证这个拉取请求中对用户API的更改”

验证代理工作流：
1. 读取项目的README/package.json获取构建和测试命令
2. 运行构建 - 如果失败则立即返回FAIL
3. 启动后端服务器
4. 针对用户端点执行验证策略：
   - 创建用户：POST /users - 验证响应形状和状态码
   - 获取用户：GET /users/{id} - 验证返回的数据结构
   - 更新用户：PUT /users/{id} - 测试边缘情况和错误处理
   - 删除用户：DELETE /users/{id} - 验证正确删除
   - 无效输入测试：测试格式错误、缺失字段等
   - 认证和授权测试（如果适用）
5. 运行后端测试套件
6. 检查日志中是否有错误或警告
7. 停止服务器并清理资源
8. 提供详细的验证报告，列出任何发现的问题

### 示例2：验证前端更改
用户请求：“验证这个拉取请求中对仪表板UI的更改”

验证代理工作流：
1. 读取项目文档获取构建和启动命令
2. 运行构建 - 如果失败则立即返回FAIL
3. 启动前端开发服务器
4. 如果可用，使用浏览器自动化：
   - 导航到仪表板页面
   - 截图关键区域
   - 点击所有交互元素（按钮、链接、表单等）
   - 读取控制台日志查找错误
   - 验证路由和状态管理
5. curl 静态资源和API端点以确保它们可访问
6. 运行前端测试套件（如 Jest、React Testing Library等）
7. 检查是否有未处理的承诺或内存泄漏
8. 停止服务器并清理资源
9. 提供详细的验证报告，列出任何发现的问题

### 示例3：验证重构（无行为变化）
用户请求：“验证这个服务类的重构是否保持行为不变”

验证代理工作流：
1. 确保现有测试套件完全未更改地通过
2. 验证公共API表面没有变化（没有新增/删除的导出）
3. 抽样检查可观察行为：
   - 选择代表性的输入场景
   - 在重构前和重构后的版本上运行相同的输入
   - 验证输出完全相同
4. 检查是否有副作用（如对全局状态的意外更改）
5. 提供验证报告，确认行为是否得以保存

## 与pi agent的集成

要将这些增强功能集成到pi agent中：
1. 创建验证代理的核心组件
2. 实施特定于更改类型的验证策略
3. 添加临时目录隔离和安全实验支持
4. 实施全面的质量门和自动化检查
5. 与协调者-工作者模式和现有工具集成
6. 提供用于配置验证行为和严格程度的选项
7. 确保适当的错误处理和后备机制

此技能作为实施这些更改的规范和参考。
